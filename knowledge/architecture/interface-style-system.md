# Interface Style System

## Quiet resting-state hierarchy

Imported UI Style documents may customize interaction feedback, but they do not own the default emphasis of ubiquitous secondary actions. During canonicalization, `navigationItem`, `navigationAction`, `control`, `toggle`, `menuTrigger`, `menuItem`, and `roomChoice` inherit their `resting` treatment from the matching role in the selected built-in `basedOn` document. `compoundControl` instead inherits that built-in document's ordinary `control.resting`: this keeps the top Start/Open split controls quiet even when `basedOn: nostalgia` gives its built-in compound plate permanent relief. Their plate becomes prominent on hover or while a menu is expanded, not merely because they are structurally compound. Imported radius and `hover`/`active`/`selected` treatments remain effective. `primaryAction` is excluded because a true primary operation may intentionally keep a visible resting plate. This normalization also applies to already persisted custom documents, so a loud imported resting state cannot make every ordinary button compete with hover or selected state.

Quiet resting does not mean flat state feedback. `toggle`, `menuTrigger`, `menuItem`, and `roomChoice` inherit the complete corresponding `basedOn` selected treatment when an import omits `selected`; they never fall back to the newly quiet resting state. If an import provides a non-transparent selected treatment but leaves its depth at `none`, canonicalization inherits only the corresponding role's `selected`, then `active`, then `resting` elevation from `basedOn`, while preserving the imported surface, border, and radius. This follows the existing Retro/Nostalgia language: hover is raised feedback, while an enabled or chosen state is normally held down/inset. An explicit non-none imported elevation remains authoritative. `aria-pressed`, `aria-checked`, and `aria-selected` consume these selected treatments. Composer popover triggers that are structurally ordinary `.kimix-control-button` controls also map `aria-expanded=true` to `menuTrigger.selected`, so an open menu stays visually distinct until it closes.

Role ownership must also be exclusive at the CSS consumer layer. `.kimix-state-button` may retain `.kimix-icon-text-button` for geometry, but it is excluded from the generic control resting/hover/active selectors; otherwise specificity contributed by generic `:not(...)` filters can override the dedicated toggle `[aria-pressed=true]` treatment. Toggle visuals are owned only by the toggle state matrix.

Kimix keeps color token generation and interface-material compilation as separate runtime systems, but a custom style document may carry one recommended three-seed palette. A color theme still exclusively owns surface, text, accent, semantic, and border tokens; an interface style still owns shape and texture: radius, shadow, edge treatment, and role-specific control depth. Selecting or importing a custom style atomically selects its associated `ui-style:<id>` palette so the first rendering matches the authored visual direction. Users may then override it with any ordinary palette. Leaving the style clears its owned palette only when that palette is still active, so a manual override is preserved.

# Style Contract

The contract has three layers. Theme tokens (`--surface-*`, `--text-*`, `--accent-*`, and `--border-*`) remain the only color authority. Semantic interface tokens (`--ui-control-*`, `--ui-compound-*`, `--ui-nav-action-*`, `--ui-nav-list-*`, `--ui-selection-*`, `--ui-toggle-*`, `--ui-popup-*`, `--ui-field-*`, `--ui-menu-trigger-*`, and `--ui-shell-*`) describe how a role should feel. Components enroll through role classes such as `.kimix-window-control`, `.kimix-split-control`, `.kimix-sidebar-nav-item`, `.kimix-sidebar-project-row`, `.kimix-menu-panel`, and `.kimix-modal-card`.

Adding a style preset therefore starts by overriding the semantic interface tokens at its root attribute. Component-specific preset selectors are reserved for a genuine signature device or a structural exception that cannot be expressed by the contract; they are not the default integration mechanism.

# Importable Style Contract

UI Style v1 is the only data boundary for imported interface styles. `src/utils/uiStyleContract.ts` owns the strict versioned schema and compiles accepted material fields into `--ui-*` variables. The only accepted color values are `palette.primary`, `palette.surface`, and `palette.accent`, each a complete `#RRGGBB` seed consumed by the existing light/dark theme-token builders; arbitrary color fields, CSS, selectors, URLs, scripts, fonts, spacing, and layout instructions remain forbidden. Shape primitives are bounded numeric radii and border widths. Depth is a structured kind/depth/opacity tuple whose highlight and shadow colors are always derived from the active `--surface-*`, `--text-*`, and `--border-*` theme tokens. Motion uses bounded durations and an easing allowlist.

Every document declares a built-in `basedOn` baseline and role treatments. `src/utils/builtinUiStyleDocuments.ts` defines complete v1 documents for Default, Modern, Retro, and Nostalgia so custom documents can inherit a protected baseline and the AI prompt can expose a complete template. Rendering ownership remains deliberately asymmetric for compatibility: Default uses the unscoped baseline and Modern/Retro/Nostalgia retain their previously validated preset CSS; only `custom:*` compiles the selected document to inline `--ui-*` and activates the fixed consumer layer through `data-ui-style-contract="v1"`. Consumer selectors begin with `:root[data-ui-style-contract="v1"]`: the direct root marker provides custom-only isolation, while the combined pseudo-class and attribute specificity reliably beats base component shape declarations that occur later in the stylesheet. Do not wrap these root-ancestor selectors in `@scope` rooted at the same element; the scope root will not match that ancestor form and the variables will load without being consumed. Missing custom roles inherit from the declared baseline during canonicalization; the canonical persisted copy materializes every role, making later rendering deterministic. The public role catalog covers shell, toolbar, navigation items/actions, ordinary and compound controls, toggles, fields, cards/sections/events, popups/menu items/modals, Composer/message/status/Markdown surfaces, inspectors, toast/dock, and Multi-Agent choices.

The shell radius is decided solely by the renderer on Windows. Kimix uses a transparent frameless browser window (`transparent: true` with `backgroundColor: "#00000000"`; the renderer flags `data-transparent-shell="1"` so `html/body` keep no surface color) and the outer `.kimix-app-shell` consumes `--kimix-window-corner-radius` (built-in Default/Modern 16/20px, Retro 6px, Nostalgia 0px, custom 0-32px through the v1 contract). The transparent-shell `body` is also the universal viewport clip owner: its `clip-path` consumes the same radius so viewport-fixed layers and portals mounted outside `.kimix-app-shell` cannot repaint the transparent corner pixels. The physical corner curve is therefore a smooth antialiased CSS radius identical to the adjacent workspace surface, and maximizing removes both the body clip and shell radius through `[data-window-maximized]`. Because the transparent HWND has no useful DWM frame and any outside shadow is clipped, a pointer-transparent `::after` overlay draws one neutral 1px inset ring above shell children; it follows the same radius, uses black alpha in light mode and white alpha in dark mode, occupies no layout, and is disabled when maximized. Kimix must not translate style radii into `BrowserWindow.setShape()`: a custom HWND region cannot cover the DWM border and shadow that Windows draws around the window rectangle, leaving a visible light band next to the edge on dark desktops, while `SetWindowRgn` clipping never reaches outside the HWND rectangle anyway (v2.21.105 and v2.21.109 lesson). Transparent windows lose the DWM system shadow; resize and maximize were verified clean at 100% DPI and that shadow absence is accepted for corner fidelity. Non-Windows platforms keep native window frames and the body surface color.

Windows taskbar identity has one ID and one icon source. `app.setAppUserModelId("com.kimix.app")` is applied only when packaged and must remain equal to electron-builder `appId`; dev deliberately avoids a process AUMID because its carrier is `electron.exe`. Every window still loads one checked NativeImage from `APP_ICON_PATH` (dev `build/icon.ico`, packaged `resources/icon.ico`) and binds it both through the BrowserWindow constructor and the Windows `setIcon()` / `setAppDetails({ appId, appIconPath, appIconIndex: 0 })` taskbar-button path. This explicit window binding is required for frameless transparent windows and portable launches: the packaged EXE and shortcut may both contain the correct Kimix icon while the live taskbar button otherwise falls back to the Electron host icon. Portable and installed builds keep the same AUMID instead of creating separate taskbar groups.

Imported documents are parsed in the Electron main process with a JSON-only 256 KB boundary, canonicalized, then persisted inside Kimix settings rather than referenced through the original file path. `custom:<id>` is the selected-style identity and `ui-style:<id>` is its palette identity. Historical documents that omit `palette` remain valid under schema v1 and canonicalize to the project default Warm Paper seeds; this is deterministic migration, never a capture of whichever palette happened to be active. The first-paint theme snapshot stores only the active custom document, which is sufficient to resolve its owned palette; authoritative settings retain the full custom library. The color-settings grid appends only the currently selected custom style's owned palette and marks it `风格化自带`; palettes from other custom styles stay hidden. Deleting a custom document removes only that library entry and falls back to Default plus Warm Paper when its style/palette was active. Built-in documents never enter the delete path. The AI-generation prompt is produced from the current schema, role catalog, complete role-to-touchpoint guide, palette requirements, and full template so a schema change cannot silently leave prompt coverage behind. It asks for intentional role overrides only; omitted roles inherit `basedOn`, avoiding blind full-document rewrites. It also imposes hard legibility constraints: palette seeds must keep text readable under both auto-derived light and dark modes, adjacent container tiers (page ground, section card, popup) must remain visually separable instead of sharing one surface with all borders `none`, and state feedback must be perceptible — hover/active/selected must differ clearly from resting and a selected item must be recognizable at a glance, with `subtle` borders still visible on the chosen surface. Its delivery contract is inbox-first: a capable Agent writes `kimix-ui-style-<id>.json` into the Kimix style inbox directory (`~/.kimix/ui-styles/`, whose absolute path is embedded in the prompt) and returns only the path; writing into the current workspace or an inline JSON code block are fallbacks reserved for environments without access to that directory. The main process owns the inbox (`electron/uiStyleInbox.ts`): an `fs.watch` with a 600 ms debounce and content-fingerprint dedup broadcasts new or changed documents over `kimix:ui-style-inbox`, while the renderer's `useUiStyleInboxSync` upserts unknown ids through the same store action as manual import (which auto-applies the style and its owned palette) and updates only the stored document for a known id, never hijacking the user's current style selection. A startup scan covers files written while the app was closed. Deleting a custom style in Settings also deletes inbox files whose parsed document id matches, so a later scan cannot resurrect it. Inbox synchronization (startup scan and broadcast subscription alike) waits for the first settings hydration — the `settingsHydrated` store flag set by `useBootstrap` once `getSettings` settles — because before hydration `customUiStyles` holds only the first-paint snapshot's active document, and an early scan would misread already-imported styles as new ids, re-toast the import, hijack the active selection through the upsert path, and let `useSettingsSync` write the truncated library back to disk.

# Invariants

* Appearance settings preserve separate ownership sections even though custom-style selection has one explicit palette linkage. `主题` owns light/dark/system mode; `界面风格` owns material presets and JSON/AI import; `显示与阅读` owns font size and chat navigation rail; `色彩方案` owns palette choice, the current style-owned palette card, and official-theme scanning. Each is a distinct `SettingsSectionId`, focus/search target, and draggable section. Readability or navigation preferences must never be appended inside the interface-style section merely because they are visually observable.
* A style-owned palette has one valid owner. `ui-style:<id>` may resolve only from the matching `custom:<id>` document; selection/import activates it atomically, leaving the custom style resets it to Warm Paper only if no manual palette has replaced it, and deletion clears both active identities. Missing or mismatched style palette IDs fall back to Warm Paper during settings load and token resolution. The ordinary `custom` palette is never overwritten to emulate this linkage.
* Interface-style root blocks must not assign `--surface-*`, `--text-*`, `--accent-*`, or `--border-*` color tokens. Dark theme color ownership still requires an elevated ladder: ground/base/elevated/hover must stay distinguishable, borders lift toward white (not crush into the fill), and muted text should remain near WCAG AA on elevated surfaces. Dark tokens are produced by `buildDarkTokens` / the `[data-theme="dark"]` baseline, not by style presets. Style rules consume those tokens and may use neutral transparent light/dark overlays only to express depth.
* The importable V1 consumer layer is opt-in, never a replacement baseline. Only an existing `custom:*` document may set `data-ui-style-contract="v1"` and inline compiled variables. Default must have neither style attribute nor compiled variables; protected built-ins keep only their existing `data-ui-style` identity and dedicated CSS. Switching away from a custom style or failing to resolve one must clear the contract marker and every previously applied inline variable before the fallback renders.
* Imported style descriptions are bounded metadata, not layout content. UI Style v1 rejects new descriptions above 48 characters; persisted pre-limit documents are truncated to 48 during normalization so tightening the schema cannot delete an active custom style. Settings cards are fixed at 76px, render the description as one ellipsized line, and expose the complete normalized string through a title tooltip. The AI prompt declares the same hard limit and warns that longer files are rejected.
* Visual treatment is assigned by component role, not by global element selectors. Rules such as `[data-ui-style] button`, `[data-ui-style] textarea`, or a global `.kimix-icon-text-button` skin are prohibited because the same primitives serve unrelated roles across navigation, forms, dialogs, and primary actions.
* A nested control has one visible boundary owner. In the Composer, `.kimix-composer-card` owns border, focus, and elevation; `.kimix-composer-input` remains borderless and transparent. Settings inputs own their own inset boundary because they are standalone fields.
* The Composer single-boundary rule is enforced below the data contract, not requested from style authors. `.kimix-composer-input` permanently has zero border/radius/shadow and a transparent background across resting/focus/focus-visible; the custom `field` role never selects it. Imported JSON may style only the outer `composer` role, so an AI-generated document cannot recreate the nested textarea frame.
* Controls with the same role share one state language. `.kimix-control-button` represents a tool that opens more controls, while `.kimix-state-button` represents a binary mode and derives its selected appearance from `aria-pressed="true"`. Business components must not reconstruct selected borders, backgrounds, or shadows through inline styles.
* Parent-row reveal is visibility, not interaction state. Sidebar project/session actions that appear together when their row is hovered use `.kimix-sidebar-reveal-action`: under the imported-style contract their non-hovered/non-focused resting plate is forced transparent while preserving geometry, and only the individual action's hover, focus, or active state may consume `navigationAction` / `control` material. Always-visible sidebar actions and ordinary inline controls retain their configured resting treatment.
* Imported toggle roles consume all four interaction states. `.kimix-state-button` and `.kimix-settings-permission` use resting at rest, hover only while unselected, active while pressed, and selected for `aria-pressed=true`; selected hover must remain selected. Swarm, Plan, and Tower are the canonical Composer touchpoints. Their toolbar-local `.kimix-composer-mode-button` class keeps toggle ownership of border, background, shadow, color, and pressed-state feedback, but consumes `--ui-role-control-radius` so its geometry matches the adjacent 32px thinking control. This exception is local to `.kimix-composer-toolbar-secondary`; popover and Settings toggles keep the authored toggle radius.
* A compound button cannot silently lose the interaction material of adjacent controls through an AI omission. During custom canonicalization, a compoundControl hover/active treatment with non-transparent surface + visible border + elevation none inherits the matching control elevation when that control has depth. Its resting treatment still inherits the quiet built-in baseline. The top Start/Open split controls consume compound resting/hover/active states, while menu-expanded state deliberately reuses hover chrome.
* Message copy actions share one compact geometry. User-message copy and Assistant single-copy are 28×28 square icon controls; Assistant copy-all may retain its text label but is exactly 28px high. The Assistant pair uses `.kimix-message-copy-action` plus the control role so both buttons receive the same preset material, border, radius, and shadow; `is-roomy` is not allowed on the single-copy action.
* Composer tools are controls, including compact or popover-local variants. `.kimix-composer-tool-button` must consume the imported control role in resting, hover, and active states, while popover actions such as drawing-board ratio buttons should explicitly enroll through `.kimix-control-button`. `.kimix-icon-text-button` remains the compatibility-default control role for existing text buttons; new components should prefer the narrower semantic role when one exists.
* Imported-style completeness is enforced as a parity contract, not by screenshots. Tests compare every Kimix class used by built-in style selectors with the custom consumer block and permit only a documented structural/delegated allowlist. Interactive roles must consume their full applicable state matrix (resting, hover, active, selected or focus), not merely expose one token. Literal JSX buttons must declare a `kimix-*` role; nested text/media/semantic-color hit targets that intentionally own no independent surface must say `kimix-style-exempt`. Generic legacy rows may use a custom-only hover/active bridge, but that bridge must not assign a resting plate that turns whole content rows into raised buttons. The Agent process header and a Kimi Web foldable-thinking summary carry `.kimix-chat-standalone-disclosure` so their interaction material is explicit: resting stays transparent and shadowless (an invisible border may reserve hover geometry), hover/focus-visible consumes the complete control hover border/radius/background/shadow, and active consumes the complete active treatment. Tool, question, notification, and other collapse rows nested inside a complete card must not carry that standalone role. This interaction-only rule supersedes the v2.21.7 interpretation that gave standalone disclosures a persistent resting plate.
* Semantic-color exclusion is token-aware. Imported control consumers exclude a button only when its rendered class list contains a standalone resting `bg-accent-*` token; variant-prefixed utilities such as `hover:bg-accent-danger-light` or `hover:bg-accent-danger/10` do not make the button a solid semantic surface and must not remove it from control resting/hover/active material. This lets secondary danger/primary-text actions keep their semantic text color while receiving the selected interface style's edge, surface, and depth.
* Selection direction is semantic, not global. `--ui-selection-*` is reserved for vertical navigation; a preset may use a leading accent edge or a complete quiet pill, but it must never leak either treatment into button-like modes. Selected rows still need a distinct hover overlay via `--ui-selection-hover-*`, which must reuse ordinary list-hover chrome (`--ui-nav-list-hover-border-color` / background / shadow) rather than inventing a second deepen-only fill; keep the selection mark through `--ui-selection-hover-shadow` (default equals `--ui-selection-shadow`; Retro may compose the leading edge with the list-hover shadow). Never lock `.is-active:hover` to the resting selection fill alone. `--ui-toggle-*` is reserved for Swarm, Plan, expanded controls, and other button-like modes; it uses a complete surface and must never inherit a leading edge. `--ui-compound-*` supplies the optional shared plate and the split divider (`--ui-compound-divider-shadow`); toolbar launch/open `.kimix-split-control` must rest on the ordinary control contract and only use toggle chrome when expanded—never a permanent compound fill that reads as selected-at-rest.
* Every interactive shell touchpoint enrolls in a semantic role. Window controls and ordinary toolbar controls share the control contract; launch/open compound buttons use `.kimix-split-control`; primary sidebar actions use `.kimix-sidebar-nav-item`; project/session rows use their list roles; menu titles use `.kimix-top-menu-trigger`. A preset must not require business-component selectors to discover these surfaces.
* The Kimix default preset is a compatibility baseline, not an unscoped version of a new preset. Because `applyUiStyle("default")` removes `data-ui-style`, baseline repairs use `:root:not([data-ui-style])` and must preserve the pre-preset behavior of enrolled business roles. In particular, the session toolbar keeps its original 12px, thin-bordered controls and light hover lift; adding a preset must never make that default toolbar transparent.
* Multi-Agent room interactions have explicit role ownership. `.kimix-room-trigger` covers recipient and context-range triggers, `.kimix-room-choice` covers selectable model/permission/message options, `.kimix-room-secondary-action` covers close/cancel/configuration actions, and `.kimix-room-primary-action` covers add/save actions. Roles in the same feature do not automatically share material: Composer room triggers follow adjacent toolbar controls and stay flat at rest, while dialog secondary actions may retain a complete boundary. Room components must not depend only on generic Tailwind radius, border, or hover utilities.
* Floating surfaces share a semantic skeleton before any style preset is applied. Small menus use `.kimix-menu-panel` and `.kimix-menu-item`; popovers use `.kimix-floating-panel`; dialogs use `.kimix-modal-card`; Diff and long-task sidebars use the inspector role. The default Kimix style defines spacing, radius, elevation, and interaction states for these roles, and interface presets may change their material without changing their structure. Any later public-shell declaration that requires `!important` must itself consume `--ui-role-popup-*`, `--ui-role-modal-*`, or `--ui-role-inspector-*` with an explicit default-token fallback; relying on the earlier custom selector to beat a fixed important value makes the inside style correctly while leaving the outer shell at its baseline. Runtime error dialogs are modal surfaces, never interactive cards: they must not acquire hover/active card material merely because the pointer crosses the dialog body.
* The inspector role is reserved for standalone panels, never for flush embedded panes. `.kimix-longtask-inspector` and `.kimix-diff-panel` are standalone surfaces and consume the full inspector border/radius/shadow. `.kimix-model-provider-sidebar` is a flush pane clipped by the provider manager card's `overflow: hidden`; giving it the inspector role's own complete rounded frame produced doubled borders and mismatched corner crescents under custom styles (fixed in v2.21.142). A flush child clipped by its parent must stay radius-zero and shadowless with only its separator edge.
* Content surfaces enroll by ownership instead of rebuilding a card from Tailwind utilities. `.kimix-section-card` owns the complete neutral surface of a standalone content section, including its theme-derived border and background. `.kimix-event-card` owns only radius and depth for approval, question, error, recommendation, and recovery cards because those roles retain their own semantic border and background colors. `.kimix-inset-section` is the borderless background layer for content nested inside a complete card. Workspace segmented shells (`.kimix-settings-theme-grid` and `.kimix-settings-permissions`) consume `insetSection` border/background/depth through an explicit `.kimix-settings-panel.is-workspace` scope: putting that multi-class branch inside zero-specificity `:where(...)` lets the three-class base selector silently restore defaults. Radius still follows local geometry: a theme grid with visible inset derives `outer radius = interactiveCard radius + inset` (currently 6px), while a full-bleed permissions list directly uses the `insetSection` radius and clips its square child rows. Never force padded and full-bleed shells through one radius declaration merely because they share material. Settings search and color-value shells consume the `field` role even when their outer element is a `div` or read-only `span`; the role follows visual ownership rather than tag name. Inputs, clickable choices, dividers, and explanatory blocks nested inside a bordered floating or modal shell must not reuse either complete-card role.
* A styled container does not implicitly style its interactive descendants. Dense action matrices inside `.kimix-longtask-inspector .kimix-section-card` enroll through explicit roles: plain icon-text controls stay flat at rest under the inspector scope, while grouped secondary matrices and header refresh chips use `.kimix-inspector-action` for a quiet resting chip (`--surface-base` + subtle border). Clickable rows (session-tree children, recent diffs, file picks) use `.kimix-inspector-list-item`. Header 32px icon buttons use `.kimix-inline-icon-action.is-roomy` so Modern/Retro can own their radius and hover tactile treatment. Neutral nested blocks use `.kimix-inset-section` instead of ad-hoc bordered cards. Solid primary actions (`.bg-accent-primary`) stay excluded from the secondary skin. Standalone inspector inputs enroll through `.kimix-inspector-field`, and card drag handles through `.kimix-inspector-drag-handle`. The scope must retain both inspector and section ownership; a preset must never promote this exception into a global `.kimix-icon-text-button` skin. Do not restyle matrix chips with permanent `bg-accent-primary-light` utility fills.
* Every text input must enroll in a field role class (`.kimix-settings-input`, `.kimix-inspector-field`, or the `.kimix-settings-search` container) instead of ad-hoc Tailwind borders with hardcoded `focus:border-accent-*`: both built-in preset CSS and the imported-style contract only theme those classes, so stray inputs keep an unthemed accent ring under every preset (fixed in v2.21.62 for the plugin-store, dialog-command, and inspector git-commit fields). Field focus selectors use `:is(:focus, :focus-within)` so a field-class wrapper around a transparent inner input is themed too.
* Once a shell or media surface has a semantic role, business components must not override it with fixed `rounded-[Npx]` or `shadow-[...]` utilities. `.kimix-app-shell-main`, `.kimix-modal-card`, `.kimix-onboarding-card`, `.kimix-floating-panel`, and `.kimix-media-thumb` own those properties centrally. Role ownership also imposes a compile-time radius ceiling: only fixed-height navigation/actions/controls/toggles/menu triggers/status pills may keep an unbounded `pill`; content-bearing roles are capped by semantic scale (20–24px for cards/code/tables/menu rows, 28px for modal/composer/userBubble/popup/inspector/toast/dock, 32px for shell). This compiler clamp applies to persisted imports too, so assigning `pill=999` to a user bubble can never turn a long message into a half-circle or push text into the curved edge. Context-specific geometry such as circular preview controls, progress tracks, or a two-pixel status mark remains a legitimate local exception.
* Composer send, steer, and stop remain circular primary actions. ContextBar is one continuous control strip whose child actions become distinct only on hover or expanded state. ContextBar triggers expose `aria-expanded` so workspaces, usage, models, and later additions share the same open state treatment.
* Sidebar projects and sessions use one active-state grammar per preset. Default and Retro use a quiet selected surface plus one accent edge; Modern uses the Codex-style complete quiet pill with no directional marker. Active navigation must not stack a full outline, inset frame, and focus ring to communicate the same state.
* Compound states have explicit precedence. For project and session rows, `.is-active:hover` consumes the same `--ui-selection-*` tokens as `.is-active`; hover must never replace the complete `box-shadow` and erase the active accent edge. Expanded and pressed toolbar controls keep their own `--ui-toggle-*` state when hovered.
* Shell separation must communicate real structure. The sidebar does not draw a decorative full-height rule; `--ui-shell-divider` remains `none` unless a preset can justify the divider semantically. Separators inside split controls and menus use their dedicated role tokens and remain local to the grouped content. A panel resize handle is primarily an interaction overlay rather than a visible layout column: the left sidebar handle has zero net flex width and overlaps the main shell, while the right-inspector variant deliberately keeps a 4px ground-colored seam between the main shell and either right panel. Both variants retain the same 12px pointer target by overlapping the following panel, stay out of the preceding panel's edge scrollbar, and center their hover hairline on their respective boundary/seam. The session inspector and file-preview panel share one width owner plus the same header (`18/14px`) and body (`18px`, top `14px`, bottom `20px`) outer insets so switching panel type cannot shift the content grid.
* Full-page workspaces share one identity hierarchy. Plugins, Hooks, and Settings place the workspace icon, title, concise scope description, and return action in `.kimix-workspace-header`. A replacement settings sidebar may retain its local return/title context because it replaces the global navigation shell, then owns search and section navigation below it. The scrollable body starts directly with the selected section's controls; it must not repeat the active sidebar page label and description as a second heading. Page-specific action groups such as model diagnosis remain available in a compact toolbar without restoring that duplicate heading.
* A resizable settings sidebar has one right-side inset owner. The sidebar shell follows the live shell width and contributes no extra right padding; header, search, navigation, and version groups align to the same 8px visual boundary. The scroll container's stable scrollbar gutter is itself that right-side inset, so it must not stack another right padding on top. Navigation/search-result rows remain `width: 100%` inside the resulting content box and therefore grow or shrink with the dragged sidebar width.
* The settings workspace sidebar enrolls in the same navigation roles as the primary sidebar: the return action and collapsed page icons consume `--ui-nav-action-*`, section items and search results consume `--ui-nav-list-*`, and the active page consumes `--ui-selection-*` including `.is-active:hover`. Settings must not hard-code `surface-hover` chrome that bypasses preset tokens. Nostalgia additionally renders the `.kimix-workspace-header` return action as a raised resting button because it is the page-level primary navigation control shared by Settings, Hooks, and Skills.
* The chat toolbar bottom rule is a structural boundary between navigation/actions and conversation content, so every preset keeps it. Split-control dividers are a separate role owned by `--ui-compound-divider-shadow`: Modern may set that local divider to `none` for a seamless Codex-style compound control, while Default and Retro may retain it. The divider shadow is rendered on a centered 1×16px square-corner pseudo-element, never on the rounded secondary button itself; otherwise the shadow follows that button's rounded top/bottom edge and produces hooked caps. A request about one divider must not be implemented by removing another boundary at a different hierarchy.
* A structural shell border is indivisible. Removing an ornamental sidebar divider must never be implemented by clearing one edge of `.kimix-app-shell-main`; every preset keeps the shell's four structural edges intact and controls ornamental separation through `--ui-shell-divider` or a dedicated spacer. Full-width toolbar/footer regions nested inside that shell do not own four-corner silhouettes: their own radius is zero, the parent's `overflow-hidden` clips the true top/bottom exterior corners, and the toolbar's bottom edge plus footer's top edge remain straight. Applying the generic toolbar radius to all four child corners creates false rounded seams inside one continuous shell.
* Renderer geometry and operating-system window geometry have separate owners. On Windows the approved boundary is a frameless transparent BrowserWindow whose visible corner and 1px inset outline are renderer-owned; DWM still owns the HWND rectangle, hit testing, and taskbar integration. Do not bridge style radii back into native geometry with `BrowserWindow.setShape()` or a `roundedCorners: false` override, and do not use an outward renderer shadow that the HWND clips. Non-Windows platforms retain native outer chrome.
* Retro styling uses a restrained signature language: the subtle Platinum title-bar stripe and the inset accent strip on selected vertical navigation rows. Sidebars, window controls, ordinary toolbar actions, split launch/open controls at rest, and content surfaces stay flat at rest; hover, active state, expanded split menus, and floating surfaces carry the tactile treatment. Enrolling a role must not make its boundary permanently visible.
* Nostalgia (怀旧) uses a Windows 95/98 classic-control language without locking the teal/gray system palette: zero radius, hard raised bevels (light top-left / dark bottom-right) on resting controls and cards, sunken fields and pressed states that invert the bevel, hard offset popup shadows, and solid selected faces without Retro's leading accent edge. Like other presets it may only use neutral light/dark overlays for depth and must not assign `--surface-*` / `--text-*` / `--accent-*` / `--border-*` source tokens. It must remain visually distinct from Retro: Retro is soft small-radius Platinum that stays flat at rest; Nostalgia is square and embossed at rest.
* Style-specific selection adornments must be preset-owned. The default `:root` contract and Modern keep `--ui-selection-shadow: none`; Retro alone may add the inset accent strip to selected vertical navigation rows. Shared components consume the token and must not hard-code that strip.
* Retro button hover is one shared interaction language, not a component-by-component exception. Control, navigation-action, navigation-list, menu-trigger, context-bar, collapsible-header, and standalone utility-button roles consume the same Retro hover border/background/shadow tokens. Every enrolled role must transition `box-shadow` with the shared 150 ms hover timing so the tactile surface interpolates instead of snapping. The standalone utility allowlist must keep its preset scope inside `:where(...)`: a button may also carry a bordered control role, whose later structural contract must win and prevent a real 1px border plus a 1px shadow ring from stacking into a thick outline. Binary state buttons are not fallback utilities: their unpressed hover uses the tactile Retro control language, while `aria-pressed="true"` keeps the shared Kimix accent-colored selected state so interaction availability and persistent state cannot be confused. Never use a global native `button:hover` ring as fallback: interactive rows may contain nested button hit targets, and only the outer visual surface may own the hover boundary. New standalone buttons must enroll in a semantic button role explicitly.
* Menu-item hover belongs to the same per-preset language instead of a flat `--surface-hover` fill: Retro `.kimix-menu-item:hover` uses the shared hover background plus the outline-and-inset shadow, and Nostalgia uses the raised bevel; checked/selected rows keep their own leading-edge or sunken treatment (the hover rule must exclude them), and danger items keep their semantic fill. Solid primary buttons (`button.bg-accent-primary`) are the one colored-control exception to "flat utilities": presets may add shape-only chrome — Retro's top-highlight plus drop shadow and Nostalgia's raised-at-rest / sunken-on-active bevel — while the accent fill itself stays theme-owned and is never reassigned.
* The bottom context bar is a layout group rather than a panel surface. Retro may style each contained action on hover or expansion, but the bar itself remains transparent, borderless, and shadowless so it does not add a second frame beneath the Composer.
* Modern styling uses a Codex-inspired shell language: a complete navigation pill, 18–20px content/composer shells, quiet flat controls, and softly elevated floating surfaces. It may add neutral translucent depth overlays, but it must not redefine theme color tokens or restructure business layouts such as Skills cards and settings sections.
* A preset may redistribute existing theme surfaces without becoming a color theme. Modern derives `--kimix-modern-workspace-background` only from `--surface-elevated` and `--surface-base`, then uses that brighter presentation surface for chat, settings, Plugins, and Hooks while leaving the sidebar on `--surface-ground`. It must never assign a new value to any `--surface-*`, `--text-*`, `--accent-*`, or `--border-*` source token.
* Modern message surfaces use an explicit two-level hierarchy without becoming a new color theme. Neutral message metadata and Assistant inline-code shadows share `--kimix-modern-message-meta-background`; user prompts use `--kimix-modern-user-bubble-background`. Both derive directly from the active palette's `--surface-hover` and `--surface-elevated`, while the user surface keeps a lower hover weight than metadata/code. Avoid nested color mixing here: it hides the effective contrast and can make the user surface collapse into the workspace. All three stay borderless and shadowless.
* Modern radii are role-scoped instead of globally inflated: controls use 10px, cards 14px, panels 18px, and the main shell 20px. Generic `rounded-*` utilities keep a monotonic small-to-large scale and must not be used as a substitute for shell-role tokens.
* Nested radii remain concentric where two adjacent surfaces are simultaneously visible. The invariant is `outer radius = inner radius + visible inset`; the settings theme segment is the canonical example at 16px outer, 10px inner, and 6px inset. A full-bleed child clipped by its parent is not a second nested surface. Interactive press feedback uses the existing `scale: 0.96` convention, and transitions name only the properties that change.
* Modern content surfaces must enroll by semantic depth: grouped settings selectors use the 16px segment role, standalone content cards use 14px, and complete sub-region containers use 18px. New bordered or filled surfaces must not silently fall back to a generic small radius.
* Markdown tables expose frame, table, header, and cell roles before presets style them. Modern tables are page-aligned reading structures rather than cards: no outer frame, vertical grid, header fill, or zebra striping; a theme-derived subtle horizontal rule carries row separation. Default and Retro may retain their own grid treatment.

# Main Components

* `src/index.css` defines style tokens and component-role selectors.
* `src/utils/uiStyleContract.ts` defines UI Style v1 validation and safe variable compilation.
* `src/utils/builtinUiStyleDocuments.ts` defines the four protected built-in documents, custom canonicalization, and the schema-derived AI prompt.
* `src/utils/uiStyles.ts` resolves built-in/custom identities and applies compiled variables to the root attribute.
* `electron/main.ts` owns the platform window boundary and keeps Windows DWM geometry, taskbar presence, and the Kimix icon intact instead of deriving HWND regions from style documents.
* `src/utils/themePalettes.ts` resolves `ui-style:<id>` through the matching custom document and generates light/dark color tokens without transferring color ownership into style CSS.
* `src/components/chat/Composer.tsx`, `ContextRing.tsx`, and `ContextBar.tsx` expose role-specific controls and expanded/pressed state hooks.
* `src/components/chat/AddRoomAgentDialog.tsx`, `EditRoomAgentDialog.tsx`, `RoomAgentPicker.tsx`, and `RoomContextPicker.tsx` expose the Multi-Agent room trigger, choice, secondary-action, and primary-action roles.
* `src/components/layout/Sidebar.tsx` enrolls primary actions, projects, sessions, settings, and the project menu in navigation and popup roles.
* `src/components/layout/TopMenuBar.tsx` enrolls window controls, menu triggers, menu items, and local separators.
* `src/components/layout/SessionToolbar.tsx` enrolls launch/open split controls, utility buttons, expanded states, and dropdown menus.
* `src/components/layout/LongTaskInspectorPanel.tsx` enrolls standalone sections, dense action matrices, fields, and drag handles without transferring inspector-specific material to global controls.
* Context menus, file menus, popovers, and dialogs reuse the shared menu/popup skeleton.
